# V2｜混合检索与 Schema Linking

**这一期学会什么**：表字段召回、概念链接和 Join 正确性是三种不同问题。

## 为什么有这一期

从大 Schema 中找到正确的表、字段、值和合法关联路径。 进入条件：V1 报告与 V0 全量元数据可用。

## 本期链路

```text
Intent → Domain → Hybrid Table Search → Rerank → Column Search → Schema/Value Linking → Join Graph → SQL
```

## 跟读顺序

1. 先读 Candidate 和 SearchRepository，确认业务层不依赖 SDK。
2. 手算一个 RRF 结果，观察去重键和缺失排名的处理。
3. 跟表候选到列候选，检查连接键是否被保留。
4. 跟“苹果手机”的值映射，定位消歧与澄清分支。
5. 用明细到区域的例子读图算法，再读基数与历史关系校验。
6. 阅读消融报告，把召回改善与最终答案改善分开看。

## 必做学习实验

分别关闭 lexical 和 dense 路径，比较编码题与语义改写题；加入多事实路径，验证合法外键连接不会自动获得粒度正确标签。

记录输入、预测、实际输出、代码入口和失败原因；实验通过后再勾选相应任务。只有文档或 fake 运行不能替代真实集成与质量验收。

## 规模与验收门槛

原文目标：Domain Accuracy ≥98%、Table Recall@10 ≥97%、Column Recall ≥95%；本次约定列召回按最终上下文、macro 口径统计，必须随报告明确。

完整功能与错误场景以本期计划为准。没有实测时所有指标保持“待测”；阶段完成还需要 [通用 DoD](/plan/#definition-of-done)。

## 设计取舍

两路检索和 reranker 增加时延与运维成本。要用独立指标与消融证据证明收益；Top K 越大并非越好，上下文噪声会影响生成。

## 两分钟复述骨架

“检索决定候选，链接决定概念对应哪个对象，Join Graph 决定合法关系路径。我们用分层指标定位失败，避免把所有错误归给大模型。”

这段是练习骨架；当前未实现，不能直接当作已完成的面试经历。开发后补入你真正做过的失败实验、测试与数据。
