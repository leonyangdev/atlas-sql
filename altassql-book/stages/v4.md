## 为什么有这一期

把业务理解、查询计划、安全执行和结果验证组成可治理的生产候选系统。 进入条件：V3 稳定语义与回归集；安全基线一直保留。

## 本期链路

```text
Intent/Linking/Semantics → IR → SQL → AST → Policy → EXPLAIN → Execute → Result Validation → Answer
```

## 跟读顺序

1. 读 IR，确认复杂指标比较的计算顺序。
2. 从可信会话跟 AuthorizationContext，检查检索、缓存、SQL 和数据库防线。
3. 读 AST 血缘与默认拒绝，特别看嵌套查询、CTE、UNION。
4. 看预算如何传到数据库 timeout、取消和连接释放。
5. 读修复状态机，确认最多两次且重新验证。
6. 从结果规则跟到图表/摘要，再追溯审计与 Trace。

## 必做学习实验

以华东经理尝试华南查询，再尝试从缓存和子查询绕过；制造语法错误观察可修复链路，制造权限错误观察立即停止；验证去年为零不会输出 0% 同比。

记录输入、预测、实际输出、代码入口和失败原因；实验通过后再勾选相应任务。只有文档或 fake 运行不能替代真实集成与质量验收。

## 规模与验收门槛

完成 Enterprise NL2SQL 1.0 的验收与面试主线；“生产候选”仍需目标环境容量和安全验收。

完整功能与错误场景以本期计划为准。没有实测时所有指标保持“待测”；阶段完成还需要 [通用 DoD](/plan/#definition-of-done)。

## 设计取舍

更完整的治理会拒绝一些无法证明安全或语义完整的请求，这比给出看似顺畅却错误的答案更符合企业问数要求。EXPLAIN 估算与结果规则均有限，仍需运行和业务验收。

## 两分钟复述骨架

“我把业务计划、AST 校验、权限、成本、只读执行和结果规则分层。修复不能绕过任何防线，敏感 schema 在进入模型之前就被过滤。生产能力用安全与容量报告说明。”

这段是练习骨架；当前未实现，不能直接当作已完成的面试经历。开发后补入你真正做过的失败实验、测试与数据。
