# V3｜业务语义与可信查询

> 实现状态：待开发。此页是本期学习路线；真实代码与实测报告在完成故事后填写。

**这一期学会什么**：指标是有粒度、规则和版本的业务资产。

[打开本期 6 个故事 / 19 个任务](/plan/v3-semantics) · [查看总进度](/)

## 为什么有这一期

让“销售额怎么算”成为版本化业务资产，让生成 SQL 遵循统一口径。 进入条件：V2 召回与链接接口稳定，V0 指标草案可评审。

## 本期链路

```text
指标 Draft → Testing/回归 → 审核发布 → Semantic Retrieval + Verified Query → Context → SQL
```

## 跟读顺序

1. 从一份 net_sales 定义读表达式、过滤、允许维度和日期角色。
2. 跟生命周期服务，确认已发布版本不可原地修改。
3. 看发布如何等待索引 ready，如何失效 Redis 并保留旧版本。
4. 跟可信样例审核，再跟动态检索；确认题库泄漏边界。
5. 读 Context Builder，找到强制规则与样例证据如何进入生成器。

## 必做学习实验

保持表列不变，只改变退款或时间口径，说明为什么答案会变化；移除排除测试单的过滤，应使语义回归失败并阻断发布。

记录输入、预测、实际输出、代码入口和失败原因；实验通过后再勾选相应任务。只有文档或 fake 运行不能替代真实集成与质量验收。

## 规模与验收门槛

建立 30～50 个核心指标及累计 200+ Verified Queries（本次将最终数量目标安排于 V3），全部具有版本与审核证据。

完整功能与错误场景以本期计划为准。没有实测时所有指标保持“待测”；阶段完成还需要 [通用 DoD](/plan/#definition-of-done)。

## 设计取舍

将业务知识从 Prompt 拆出来增加治理和审核工作，却使口径可以独立测试、发布与回滚。可信查询减少重复错误，但不保证新 SQL 正确。

## 两分钟复述骨架

“V2 能找到正确字段，仍会算错指标。V3 把计算口径做成不可变版本，发布前跑回归，再把定义和兼容样例提供给生成器。”

这段是练习骨架；当前未实现，不能直接当作已完成的面试经历。开发后补入你真正做过的失败实验、测试与数据。
