## 真实入口与关键调用关系

```text
SafeQueryPipeline.run(request, context)
  ├── [generation]  BaselineSQLGenerationPipeline.run  → QueryOutcome(PROCESSING, sql)
  ├── [validation]  SQLValidator.validate(sql)
  │     ├── SQLGlot parse(dialect="postgres")      ← 语法检查
  │     ├── _reject_write_nodes                    ← DDL/DML/COPY/Transaction 拒绝
  │     ├── _validate_tables → ALLOWED_COLUMNS     ← 跨 schema / 超范围表拒绝
  │     ├── _validate_columns → ALLOWED_COLUMNS    ← 超范围字段拒绝
  │     └── _validate_functions → ALLOWED_FUNCTIONS ← 23 个允许函数白名单
  └── [execution]   AsyncpgReadOnlyExecutor.execute(validated_sql, timeout_ms)
        ├── asyncio.timeout(effective_timeout_ms)
        ├── asyncio.Semaphore(max_concurrency)     ← 并发上限
        ├── connection.transaction(readonly=True)  ← 只读事务
        ├── SET LOCAL statement_timeout            ← 数据库层超时
        └── LIMIT max_rows+1                       ← 截断检测
```

关键文件：

- `server/validation/sql.py`：SQLGlot AST 校验器，白名单拒绝，返回 `ValidatedSQL`。
- `server/execution/postgres.py`：asyncpg 只读执行器，连接池、并发门槛、结果截断。
- `server/orchestrator/pipeline.py`：`SafeQueryPipeline` 串联三层，记录各阶段耗时与状态。
- `migrations/versions/c814be6d3a92_v1_s03_s05_安全执行与trace.py`：execution_ms、referenced_tables/columns、stages、failure_category 等字段迁移。

## 逐项证据

### V1-S03-T01 SQLGlot AST 校验

`SQLValidator.validate()` 先用 SQLGlot 把 PostgreSQL SQL 解析成 AST，再按四个维度实施默认拒绝：

| 维度 | 实现 | 绕过向量覆盖 |
|------|------|-------------|
| 语句类型 | `isinstance(statement, exp.Query)` 且包含 `exp.Select` | DDL、多语句 |
| 写入节点 | `_reject_write_nodes` AST walk，拒绝 11 种节点 | 注释绕过 UPDATE、写 CTE + RETURNING |
| 表白名单 | `table.name not in ALLOWED_COLUMNS`；拒绝跨 schema/catalog | `private.fact_order`、库存表 |
| 列白名单 | `column.name not in ALLOWED_COLUMNS[table_name]` | 不存在列 `order_no`、机密列 |
| 函数白名单 | `ALLOWED_FUNCTIONS` 23 个允许函数；Anonymous 函数名 upper | `pg_sleep`、`COPY` 函数 |

校验成功返回 `ValidatedSQL(sql, tables, columns)`，规范化 SQL 由 SQLGlot `statement.sql(dialect="postgres")` 生成；执行器只接受此类型，未经校验的字符串在类型层被隔离。

### V1-S03-T02 只读账号与只读事务执行

`AsyncpgReadOnlyExecutor` 使用 reader DSN（`atlas_reader`），连接池在创建时指定：

```python
server_settings={"default_transaction_read_only": "on"}
```

每次查询额外在事务内执行 `SET LOCAL statement_timeout = <ms>`，双重保障：

- 连接池级别：`default_transaction_read_only=on` 阻止写入。
- 事务级别：`connection.transaction(readonly=True)` 显式只读。
- 超时：`asyncio.timeout` + `SET LOCAL statement_timeout` 双层，取最小值。
- 并发：`asyncio.Semaphore(max_concurrency)` 限制，超限抛 `EXECUTION_BUSY`。
- 截断：包装 `LIMIT max_rows+1`，长度超限时 `truncated=True`。
- 取消：`asyncio.CancelledError` 不被吞掉，连接归还池不污染后续请求。

### V1-S03-T03 生成→校验→执行串联，正反例验证

`SafeQueryPipeline.run()` 强制按序执行三阶段：生成阶段未返回 PROCESSING 时直接返回，校验
失败时记录失败阶段并返回，不进入执行器。每阶段均记录 `QueryStageTrace(name, status, duration_ms)`
并写入 `query_record.stages`。

正例（4 个测试用例）：

- `SELECT COUNT(*) AS total FROM fact_order` — 通过
- JOIN + GROUP BY + ORDER BY 多表查询 — 通过
- CTE（只读）— 通过
- EXISTS 子查询 — 通过

## 设计取舍与限制

- `ALLOWED_FUNCTIONS` 只开放 23 个基线需要的函数；未知函数默认拒绝，`pg_sleep`、
  文件读取和扩展函数不会被执行。
- `statement_timeout` 的值来自强校验配置，不含用户输入，直接拼入 `SET LOCAL` 是安全的。
- reader 账号本身无写权限；只读事务是额外防线，而非唯一防线。
- 超时后 `asyncio.CancelledError` 不吞掉，上层可取消；连接池 `pool_pre_ping=True` 确保超时
  请求不占用后续健康连接。
- V1 不做分页；截断 `max_rows` 为配置参数，默认 200 行。
