## 真实入口与关键调用关系

```text
SafeQueryPipeline.run
  └── stages: [generation, validation, execution]  → query_record.stages (JSON)
                                                    → query_record.execution_ms
                                                    → query_record.referenced_tables/columns
                                                    → query_record.failure_category (自动初始值)

server/api/trace.py   /api/v1/admin/traces
  GET  /api/v1/admin/traces             → 列表（status / failure_category 过滤）
  GET  /api/v1/admin/traces/{trace_id} → 详情（含 stages、referenced_tables/columns）
  PATCH /api/v1/admin/traces/{trace_id}/review → 写入 failure_category / review_note / reviewed_at

server/observability/failure.py
  suggest_failure_category(response, question)   ← 基于 error_code + referenced_tables + question.category
  FailureCategory (StrEnum 9 个分类)

apps/admin/app/traces/page.tsx          ← 管理端人工复核标签界面
  加载列表 → 点击行展开详情 → select 选分类 + 文本框备注 → PATCH 保存

server/evaluation/baseline.py          ← BaselineEvaluator + BaselineReport
  select_v1_cases → BaselineEvaluator.run → BaselineReport
  指标：syntax_valid_rate / execution_correct_rate / first_success_rate
        latency_p50/p95_ms / total_tokens / average_tokens
```

关键文件：

- `server/api/trace.py`：Trace 列表、详情、PATCH review 三端点，`require_admin` 守卫。
- `server/observability/failure.py`：`FailureCategory` 枚举（9 个标签）和自动初始归因函数。
- `server/evaluation/baseline.py`：`BaselineEvaluator`、`BaselineReport`、`select_v1_cases`。
- `server/evaluation/comparator.py`：行级结果比对，`compare_results`、`compare_action`。
- `apps/admin/app/traces/page.tsx`：人工复核标签前端。
- `benchmarks/v1/reviewed_failures.yaml`：10 条人工标注记录，与数据库写入一致。
- `migrations/versions/c814be6d3a92_v1_s03_s05_安全执行与trace.py`：Trace 字段迁移。

### V1-S05-T01 阶段耗时记录与管理端 Trace

| 字段 | 内容 |
|------|------|
| `stages` | `[{name, status, duration_ms}]` — 最多 3 个阶段 |
| `execution_ms` | 执行阶段耗时（ms）|

| `failure_category` | `suggest_failure_category` 自动初始值 |
| `review_note` | PATCH 后写入 |
| `reviewed_at` | PATCH 后写入（UTC） |

### V1-S05-T02 冻结 Sales 子集评测

`select_v1_cases` 按两条规则筛选可纳入基线的题目：

1. `expected_action is not None`（显式拒绝 / 澄清题）— 直接纳入
2. `gold_sql` 存在且通过 `SQLValidator.validate`（Gold SQL 在 V1 白名单可表达）— 纳入

库存表、跨域字段的 Gold SQL 被 validator 拦截，不进入指标分母，保证分母与测试集实际能力匹配。

`test_v1_case_selection_is_fixed_by_ast_scope`：构造含 3 道题的 fixture（2 道 Sales 可表达 +
1 道库存域），断言只选出 2 道，分母准确。

指标定义（`_metrics`）：

### V1-S05-T03 人工复核失败，标注 10 条

**管理端 PATCH 流程**：

```text
PATCH /api/v1/admin/traces/{trace_id}/review
  body: {"failure_category": "wrong_join", "note": "..."}
→ record.failure_category = body.failure_category.value
→ record.review_note = body.note.strip()
```

**V2 工作优先级依据**（按人工复核频率排序）：

1. **指标口径与值映射**（wrong_metric 2 + wrong_value 2，4 / 10）— 最高频；根因是 Prompt 指标草案
   表述不足，V2 应注入语义模型注册表与字段值说明（如 `refund_status` 取值、`gross_amount` 含义）。
2. **时间窗**（wrong_time 1 + wrong_aggregation 中时间相关，1 / 10）— V2 应在 Prompt 中注入业务时钟
   约束（business_clock = 2026-06-30）。
3. **Join 扇出**（wrong_join，1 / 10）— V2 应在 few-shot 示例中包含正确的多表 Join 模式。
4. **行级权限**（undetermined test-030）— V4 解决，不计入 V2 优先级。

## 设计取舍与限制

- 人工复核标签针对题目语义，不依赖单次随机 trace_id；模型或 Prompt 变化后需重新复核，
  `reviewed_failures.yaml` 文件顶部有明确注记。
- `suggest_failure_category` 是辅助初始值，管理员可在界面上覆盖；不依赖它宣称分类准确率。
- 基线评测（`BaselineEvaluator.run`）需要业务库在线，当前离线断言覆盖接口和聚合逻辑；
  真实数字需在配置完整环境后运行 `uv run scripts/run_v1_baseline.py`。
- Trace 列表默认按 id 倒序、最多返回 50 条；大量历史 Trace 需使用 failure_category 过滤参数。
